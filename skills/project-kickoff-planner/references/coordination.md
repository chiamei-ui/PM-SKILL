# 協作與交接規則

## 啟動

把問題、服務對象、預期成果、最小交付、明確不做、成功證據、決策角色與限制寫清楚。按相關性檢查設計、前端、後端、CMS／資料、整合與營運；不相關項目不展開。將會改變範圍或時程的未知轉為有輸出、角色、探索時間與備案的問題，讓工程評估。

提出依賴順序與時程範圍，涵蓋確認、製作、整合、驗收與必要緩衝。區分投入工時與等待日數，以及使用者本職與 PM 工作的容量。未確認的人力與估時不可排成承諾。

## 跨角色交付介面

先確認團隊已約定的格式與管道，優先沿用。缺少約定時，提出最小版本供接收者確認：交什麼、在哪、誰接、完成條件。

| 接收者 | 提供的輸入 |
| --- | --- |
| 主管 | 痛點、目標、成果／KPI、影響、選項代價、需拍板事項與時間；技術細節只保留影響決策的部分 |
| 工程 | 可用畫面或流程、狀態與例外、預期效果、驗收、日期限制；請工程回傳可行選項、估時依據與風險 |
| 行銷／內容 | 活動目標、對象、素材／文案、發布節點、追蹤方式、規則待決事項 |
| 兼任 PM 的使用者 | 已決定／待決定／決策人、一個下一步、等待誰、備案 |

沒有測試站時，使用現有設計稿、截圖、流程或文字情境；不為交接另外建站。不要把現有畫面視為所有技術假設都可行。

## 卡關與求助

必要時沿用 BL 編號。保留原負責角色，協助不等於轉移全部責任。

草稿包含：目前卡住的工作與影響、證據／已嘗試、需要哪個角色提供什麼最小輸出、希望回覆時間、預估協助投入及待確認標記、未得到回覆的備案、參考連結。用專案合作語氣請求輸入，避免表述為私人欠人情；也不能假設對方有空或已接受指派。

完成狀態區分：草稿待發、已發等待、協助已確認、結果待驗收、已解除、已採備案。只有收到輸出並確認原工作可繼續，才標已解除。

## 變更

必要時沿用 CR 編號，保留提出日期、原因、目標關聯、影響、決策人、確認狀態與歷史。比較：

- 吸收：執行者確認無重大時程／品質影響才成立。
- 交換：寫明加入什麼、移除或延後什麼。
- 延後：有再評估觸發條件。
- 探索：先取得可行性與代價再承諾。
- 拒絕：說明與目標或必要條件不符的原因。

範圍增加而日期與容量不變，必須顯示代價。只更新受影響部分，保留原基準與待確認的新預估。
